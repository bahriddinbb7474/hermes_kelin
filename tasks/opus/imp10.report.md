# imp10 — отчёт: бот сам находит ленту по адресу сайта

## Итог

- Достаточно назвать сайт (`https://kun.uz`) — backend сам находит ленту,
  которую сайт объявляет в шапке страницы, и сохраняет **адрес ленты**, а не
  адрес сайта.
- Найденный адрес проходит ровно ту же проверку безопасности, что и введённый
  руками; главная проверка (лента объявлена на внутреннем адресе) отклоняется
  **до** запроса.
- У `daryo.uz` ленты нет вообще — ни объявления, ни по типовым адресам.
  Честный отказ там единственно возможен.
- Инструментов по-прежнему **30**, миграций нет, схема хранения не изменилась.
- Ленты и расходы заказчика не тронуты: те же две ленты, август 1 712 208 сум.

## 1. Как реализовано

`backend/external_data.py`:

| что | зачем |
|---|---|
| `_discover_feed_url(payload, base_url)` | ищет `<link rel="alternate" type="application/rss+xml\|atom+xml" href="…">` **только в шапке**: берутся первые `HTML_HEAD_SCAN_BYTES` (64 КБ) и, если встретился `</head>`, всё после него отбрасывается. Относительный `href` приводится к абсолютному через `urljoin`. Берётся первая объявленная лента, остальные игнорируются |
| `resolve_feed_url(url)` | если по адресу пришла валидная лента — возвращает её как есть (старое поведение). Иначе ищет объявление и **повторно** идёт через `_safe_feed_get(discovered)`. Один уровень: найденная лента заново на HTML не разбирается |
| `validate_user_news_feed(...)` | теперь возвращает `(feed_url, payload)` — вызывающий узнаёт фактический адрес ленты |

`backend/server.py` (`t_manage_news_sources`, ветка `add`):

- сначала резолв и валидация, потом проверка лимита — по **фактическому**
  адресу ленты, поэтому уже добавленная лента опознаётся, даже если её назвали
  адресом сайта;
- в БД уходит резолвленный `url`, `source_key` генерируется от него же.

### Где именно проходит проверка безопасности найденного адреса

Найденный в чужом HTML адрес — недоверенный ввод, и он идёт по тому же пути,
что и введённый руками:

```
resolve_feed_url → _safe_feed_get(discovered)
                     → _public_https_target()   # только https, стандартный порт,
                     │                          # DNS → все адреса обязаны быть
                     │                          # публичными, иначе отказ
                     → _https_get_pinned()      # соединение прибито к уже
                     │                          # проверенному адресу (без этого
                     │                          # второй DNS-ответ мог бы увести
                     │                          # сокет на приватный узел)
                     → редиректы ≤ 5, размер ≤ 2 МБ, таймаут 12 с
                   → _parse_feed()              # обязательный разбор RSS/Atom
```

Дополнительно: в объявлении принимается только `https://` — `http://`-ссылка
игнорируется, будто её нет. Никаких послаблений «домен уже проверен» нет:
проверяется каждый запрос отдельно.

## 2. Что оказалось у `daryo.uz`

Ленты у них нет:

| проба | результат |
|---|---|
| `https://daryo.uz` | HTML, в шапке нет ни одного `link rel=alternate` с типом RSS/Atom |
| `/rss`, `/feed`, `/rss.xml`, `/feed/`, `/ru/rss` | те же ~830 КБ HTML главной страницы (SPA отдаёт index на любой путь) |
| `/rss/all` | ошибка сервера |
| `/sitemap.xml` | карта сайта, не лента |

То есть отказ Мариям 2 августа был правильным по существу: подключать нечего.
Автообнаружение здесь не помогает — оно и не должно: угадывать адреса мы
перестали намеренно.

Для сравнения, `https://kun.uz` через автообнаружение находится сразу:
`https://kun.uz/news/rss?lang=uz`, 15 материалов.

## 3. Пять кейсов проверки

Прогон на боевом коде VPS (`/opt/hermes-mariyam`), полный путь
`t_manage_news_sources` — на тестовой БД `hermes_test`, сетевые пробы — вживую.

| # | вход | результат |
|---|---|---|
| 1 | `https://daryo.uz` | **честный отказ**: `ok=false`, `INVALID_NEWS_SOURCE`, `Манба текширувдан ўтмади`. Лента у сайта отсутствует (раздел 2). На сайте с лентой (`https://kun.uz`) — `ok=true`, сохранён `https://kun.uz/news/rss?lang=uz` |
| 2 | прямой адрес ленты `https://openai.com/news/rss.xml` | работает как раньше: `ok=true`, URL сохранён без изменений |
| 3 | сайт заведомо без ленты | тот же отказ, что в кейсе 1: узбекское сообщение без технических подробностей, `message_ru` остаётся в служебном ответе |
| 4 | `http://example.com/rss`, `http://127.0.0.1/rss`, `https://127.0.0.1/rss` | отклонены: `feed URL must use https` (первые два), `feed host resolves to a non-public address` (третий) |
| 5 | сайт, объявляющий ленту на непубличном адресе (`https://evil.test` → `https://internal.test/feed` → `10.0.0.7`) | **отклонён**: `feed host resolves to a non-public address`. По логу запросов виден только запрос к самому сайту — до внутреннего адреса дело не дошло |

Кейс 5 собран искусственно, как и требовала постановка: страница, в шапке
которой объявлена лента на внутреннем адресе. Тот же сценарий закреплён
регрессией `test_feed_declared_on_a_private_address_is_rejected`.

Тестовые ленты после прогона удалены (`rows left: 0`).

## 5. Тесты

`pytest tests`: **363 passed, 1 failed, 93 skipped**.

- новый файл `tests/test_imp10_feed_discovery.py` — 14 тестов: прямая лента без
  изменений, абсолютный и относительный `href`, Atom, «первая подходящая»,
  сайт без ленты, `http://`-объявление, один уровень поиска, окно сканирования,
  отказ на непубличном адресе, контракт 30 инструментов;
- упавший — `tests/test_cron_reliability.py::test_oyijon_one_shot_becomes_private_no_agent_script`,
  известный дефект окружения Windows (cp1251 в stdout дочернего процесса), к
  задаче отношения не имеет;
- существующие тесты `imp11`/`imp09` не правились: старый тест на HTML вместо
  ленты по-прежнему проходит — сообщение об ошибке сменилось с «returned invalid
  RSS» на «does not advertise an RSS or Atom feed», оба совпадают с его
  проверкой по подстроке `RSS`.
