## 1. Что оказалось за URL «ОупенЭйАй расмий хабарлари»

В `user_news_sources` у заказчика две записи:

| id | имя | URL | статус |
|---|---|---|---|
| 1 | Технология хабарлари | `https://habr.com/ru/rss/articles/` | активна |
| 3 | ОупенЭйАй расмий хабарлари | `https://openai.com/news/rss.xml` | активна |

Обе прогнал через тот же путь, что и валидация при добавлении
(`_safe_feed_get` + `_parse_feed`):

```
https://openai.com/news/rss.xml   OK  671 231 байт, 20 элементов
https://habr.com/ru/rss/articles/ OK   91 669 байт, 20 элементов
```

У OpenAI действительно есть публичная RSS-лента, она отдаёт валидный XML.
Пропуска валидации не было, записи не мусорные, удалять нечего.

Проверил заодно, доходят ли эти ленты до модели: по своей теме — да.

```
topic="технология"   -> 20 кандидатов, источник Хабр
topic="сунъий идрок" -> 20 кандидатов, источник ОупенЭйАй
```

Единственная тонкость: в дневной выборке (`topic="daily"`) их нет — там
работает фильтр по ключевым словам штатной темы. Это не дефект, но Мариям
должна передавать тему, когда Ойижон спрашивает про технику или ИИ; правку §9
предлагаю ниже.

## 2. Лента доступна сразу (пункт 1)

`external_data.invalidate_user_news_cache(user_id)` удаляет **только** ключ
`news_user:<id>`. `t_manage_news_sources` вызывает его после успешного
`add`/`disable`/`enable` (при `idempotent` — не вызывает, менять нечего) и
возвращает в ответе `cache_reset: true`, чтобы это было видно в логе.

Погода (`weather_tashkent`) и намаз (`prayer_tashkent_fatvo_v1`) — отдельные
ключи, их сброс не касается. Ограничение «не чаще раза в сутки» не нарушается:
сброс происходит только по явному действию владельца, а не по расписанию.

Риск «раскрутить внешние запросы частым добавлением/удалением» оценил и
защиту **не добавлял**: чтобы вызвать повторную сборку, нужно каждый раз
менять состав лент через модель, а сама сборка ограничена теми же 4–6 лентами;
это дешевле, чем один запрос к LLM, который для такого действия всё равно
нужен.

## 3. Кэш новостей — 30 минут (пункт 1a)

`_daily_cached` получил необязательный `ttl_seconds`. Без него — прежний
суточный контракт по календарному дню Ташкента (погода, намаз). Новости —
оба пути (offline `news:` и `news_user:<id>`) — передают
`NEWS_CACHE_TTL_SECONDS = 30 * 60`.

Заодно закрыт вопрос про параллельные запросы одной ленты: на каждый ключ
кэша заведён свой in-process lock, и после ожидания кэш перечитывается
(double-check). Если lock по какой-то причине недоступен, поведение прежнее —
просто фетч, fail-open.

Живая проверка на профиле заказчика:

```
свежая запись        -> cache hit=True
запись состарена на 31 минуту -> cache hit=False, лента пересобрана
погода (7 часов назад, тот же день) -> cache hit=True
```

## 4. Отключение штатных лент (пункт 2)

Реализовано так, как предполагала постановка — без новой таблицы и миграции.
Выключенная штатная лента хранится строкой в `user_news_sources` с ключом
самой ленты (`euronews_ru`) и `active=false`; включение обратно эту строку
удаляет. Ключи различаются по префиксу: `custom_…` — лента владельца, всё
остальное — маска штатной.

Что изменено:

- `db.manage_news_sources` получил действие `enable`, адресацию по
  `source_key`, параметр `defaults` (список штатных лент передаёт слой tools —
  хранилище само `news_sources.json` не читает) и защиту `LAST_SOURCE`;
- `list` теперь отдаёт единый список: сначала штатные ленты с их состоянием,
  затем добавленные, у каждой `kind` (`default`/`custom`), плюс `active_total`;
- `db.get_active_news_sources` фильтрует только `custom_…` — маска штатной
  ленты никогда не попадёт в список «что скачивать»;
- новый `db.get_disabled_default_keys` используется в `get_daily_news`:
  штатные ленты берутся за вычетом выключенных;
- `_fetch_news([])` (все штатные выключены, остались только свои ленты)
  возвращает корректный пустой bundle вместо ошибки;
- `manage_news_sources` в схеме инструмента: `action=add|disable|enable|list`,
  добавлен `source_key`. Инструментов по-прежнему **30**, новых не заводил.

Отключение у одного владельца не влияет на других и не трогает
`news_sources.json` — проверено запросом `get_disabled_default_keys` для
другого пользователя (пусто).

Identity guard не менялся: `manage_news_sources` уже был в `USER_SCOPED_TOOLS`,
guard подставляет только `added_by`, действия и ключи не валидирует.

## 5. Прогон на `hermes_test` (изолированно от данных заказчика)

```
1. list: 4 штатные ленты, active_total=4
2. disable euronews_ru -> kind=default, active=false; свои ленты не затронуты
3. list: Евроньюс off, остальные on
4. повторный disable -> idempotent=true
5. enable euronews_ru -> строка-маска удалена
6. выключить последнюю штатную -> LAST_SOURCE
7. добавить свою ленту -> active
8. теперь последнюю штатную выключить можно (своя остаётся)
9. list: 4 off + 1 своя on, active_total=1
10. выключить последнюю свою -> LAST_SOURCE
```

## 6. Живая проверка на профиле заказчика

Через тот же путь, что и MCP-инструменты (`t_manage_news_sources`,
`t_get_daily_news`), не через модель — доступа к Telegram у меня нет.

| # | шаг | результат |
|---|---|---|
| 0 | `list` | 4 штатные + 2 свои ленты, все активны, с `kind` и состоянием |
| 1 | новости | берутся из кэша, `fetched_at 11:08` |
| 2 | повтор сразу | `cache hit=True` — лишнего запроса нет |
| 3 | выключить Евроньюс | `ok, kind=default, active=false, cache_reset=true` |
| 4 | новости снова | `cache hit=False`, пересобраны, **Евроньюса в источниках нет** |
| 5 | `list` | Евроньюс показан выключенным, остальные включены |
| 6 | вернуть Евроньюс | `ok, active=true, cache_reset=true` |
| 7 | новости снова | Евроньюс вернулся в источники |
| 8 | масок отключения | не осталось — состояние заказчика восстановлено |

Проверки 0–6 из задания закрыты на уровне backend. **Что осталось за
заказчиком:** те же шаги словами в Telegram — как именно Мариям их
формулирует (мягкость отказа на «выключи все», текст списка лент), проверить
может только он. Тестовых лент я не заводил, убирать нечего.

Сумма расходов за август после всех проверок: **1 712 208 сум** (44 записи) —
не изменилась.

## 7. Предлагаемая правка §9 для Terra

SOUL не трогал. Предлагаю три коротких изменения:

1. **Тема при запросе.** «Если Ойижон спрашивает про тему, для которой
   подключена отдельная лента (техника, ИИ), передавай эту тему в `topic` —
   иначе материал не попадёт в дневную выборку.»
2. **Отключение любой ленты.** Сейчас §9 говорит только про «добавь или
   отключи ленту». Стоит уточнить: «Отключить и вернуть можно любую ленту,
   включая штатную — адресуй её `source_key` из `list`.»
3. **Убрать почву для «появится завтра».** Добавить: «После изменения состава
   лент новости обновляются сразу — не обещай, что материал появится завтра.»
